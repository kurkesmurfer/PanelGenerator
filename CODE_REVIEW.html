1 · What it is

A single-window AppKit editor. A PanelDocument (pure value types, JSON-persisted as .panelgen) holds a list of PanelElements. Renderer.parts(for:) turns each element into an array of ShapePart(CGPath, fill, stroke, lineWidth), and every consumer — the interactive canvas, the PNG rasteriser, the SVG writer — draws from that same array. That single design decision is the strongest thing in the codebase: the exports genuinely cannot drift from what is on screen, and it costs almost nothing in complexity.

Model.swift        value types, JSON, element catalogue & defaults
Geometry.swift     PanelMetrics (15 px/HP, 380 px 3U, 127 px 1U) + rotate/snap helpers
Renderer.swift     parts(for:) → [ShapePart]  ← single source of truth
  ├─ CanvasView.swift        909 L · editing surface, undo, selection, drag modes
  ├─ Exporters.swift         SVGExporter (via PathSVG) + PNGExporter (4×)
  └─ PaletteView / InspectorView / LayerListView / MainWindowController / AppDelegate
Selftest.swift     headless --selftest → Docs/pg_demo.{svg,png}, no window server needed

Holds up well

  • One vector path per element, shared by canvas/PNG/SVG.
  • Fill rule is non-zero on both sides, so the annulus and elbow holes survive export correctly. Line caps/joins also match CG↔SVG defaults.
  • Value-type model + apply(elements:name:) as the single mutation funnel makes undo cheap and correct for element edits.
  • Headless self-test is a real CI smoke test, not decoration.
  • Zero dependencies; make app produces a runnable bundle.
  • Commit hygiene is good — the log reads as a proper phase history.

The two structural gaps

  • No test target. Package.swift declares one executableTarget, so nothing is importable by XCTest. The path maths (elbow, ring sector, rounded rect), the JSON round-trip and the SVG numeric output are all pure functions begging to be tested.
  • No bridge to the C++ side. The document already knows every component centre; nothing emits mm2px(Vec(x,y)) lines or a Rack-helper.py components layer. See §4 — this is where the tool stops short of paying for itself.

2 · Correctness findings

SVG <text> will not render in VCV Rackcritical

Exporters.swift:47–60 · confirmed in Docs/pg_demo.svg lines 10, 11, 22

Rack renders panel SVGs through nanosvg, which has no text support at all — <text> elements are silently dropped. Every label you place disappears the moment the panel is loaded in Rack. The font-family="-apple-system, …" stack compounds it: even in renderers that do handle text, that stack resolves nowhere outside macOS.

Fix: convert text to outlines at export. CTFontCreatePathForGlyph over a CTLine's runs gives you a CGPath, which feeds straight into the existing PathSVG.d() walker — so this lands as one more ShapePart and nothing else changes. Keep the live <text> path behind an "editable text" export option for when the SVG is going into Illustrator/Inkscape instead.

MetaModule rasterises panel assets through its own SDK pipeline rather than nanosvg, so behaviour there may differ — worth verifying, but text-as-paths is correct for both targets regardless.

Panel art draws the components Rack draws on topworkflow

Renderer.swift:130–260 · conceptual

A VCV panel SVG is background only: Rack composites the real knob, jack and fader widgets over it at runtime. PanelGenerator paints jacks, knobs, faders, LEDs and screws into the exported artwork, so a straight export gives you painted knobs with live knobs sitting on top of them.

Fix: the primitives are exactly right as placement guides — keep them on canvas, exclude them from the panel export, and emit their centres separately (§4). A per-element "export: artwork / guide only" flag plus a kind-level default gets you there with a one-line change in SVGExporter.documentSVG.

Documents saved before commit 7b73f71 can no longer be openeddata loss

Model.swift:186–210 (ElementParams.segments, .layout)

Swift's synthesised Codable does not fall back to property default values for missing keys — it throws keyNotFound. isHidden and groupID are safe because they are Optional (you noted that intent in the comment), but segments and layout were added to ElementParams as non-optional CGFloat. Any .panelgen written before the button-group commit now fails to decode, and pgOpen just reports the error.

Fix: hand-write ElementParams.init(from:) using decodeIfPresent(_:) ?? default for every field, and add a schemaVersion to PanelDocument now, before there are files in the wild you care about.

Any panel-level edit wipes the entire undo stackhigh

InspectorView.swift:545–552 → CanvasView.swift:86–93

mutateDocument routes through beginLoad()/endLoad(), and endLoad() calls edits.removeAllActions() and clears the selection — that path was written for "load a file from disk", not "the user nudged a slider". So changing panel name, HP width, 1U/3U or background colour discards all undo history and deselects. The background NSColorWell is the worst case: it sends its action continuously while the picker is open, so dragging in the colour wheel wipes the stack dozens of times per second. Panel-level changes are also not themselves undoable.

Fix: give mutateDocument its own undo registration (same coalescing logic as apply) and stop reusing the load path. Changing HP width should also either clamp elements into the new bounds or flag the ones now off-panel.

Button-group parameters are unreachable in the inspectorhigh

Model.swift:104–110 vs InspectorView.swift:316, 407–425

ElementKind.category sends .pushButton and .buttonGroup to .primitive (they fall through default:), but buildParamsSection handles case .pushButton, .buttonGroup: inside the .shape branch. The Count and Layout sliders are therefore dead code — a button group can never be configured from the UI, only by hand-editing the JSON.

Fix: move that inner case into the .primitive branch. One-line move; the handlers are already correct.

Palette drag-and-drop looks broken — verifyverify first

PaletteView.swift:170–182 vs CanvasView.swift:51, 894

mouseDown creates a private NSPasteboard(name:), writes the element kind to it under Paste.elementType — and then never uses it. The actual drag is started with NSDraggingItem(pasteboardWriter: entry.kind.rawValue as NSString), and NSString's writable types are just .string. The canvas registers only registerForDraggedTypes([Paste.elementType]) and performDragOperation reads only that type, so the destination should never accept the drop. If dragging from the repo has in fact been silently doing nothing (and only double-click-to-insert works), this is why.

Fix: build an NSPasteboardItem, setString(kind.rawValue, forType: Paste.elementType), and pass that as the pasteboardWriter. Please confirm the current behaviour on-device before changing anything — I could not build here (no Swift toolchain in the bridge VM).

Elbow geometry is not dimensionally truefidelity

Renderer.swift:63–96 (sx = f.width / W, sy = f.height / H)

The elbow is built in a canonical W × H box from thickness / inner radius / arm lengths, then non-uniformly scaled into the element frame. So "Thickness = 16" only means 16 px when the frame happens to equal the canonical size; resize the element and the corner radius goes elliptical and the arm thickness changes with it. For decorative backdrops that is arguably fine — for a tool whose whole point is that px map to millimetres, it is a trap.

Fix: either drive the frame from the parameters (resize handles edit armH/armV directly), or keep the scaling but show the effective post-scale thickness in the inspector. Same class of issue in ringSectorPath (Renderer.swift:104): R = min(w,h)/2, so a non-square frame leaves the art not filling — and not matching — its own selection rectangle.

Layer list shows ~7 rows and does not scrollmedium

MainWindowController.swift:97 · LayerListView.swift:12–35

Fixed 190 pt height, rows laid out at 22 + i·22, no enclosing NSScrollView. Everything below the eighth element is drawn outside the view and is unreachable. A realistic 3U panel has 30–60 elements.

The layer list is rebuilt on every mouse-drag frameperformance

MainWindowController.swift:28–31 → LayerListView.rebuild()

canvas.onChange fires from the document didSet, which the gesture paths (mutateFrames, updatePrimaryFrame, group resize/rotate) hit on every mouseDragged. rebuild() tears down and re-creates an NSTextField and three NSButtons per row each time. Dragging a selection across a busy panel is doing hundreds of view allocations per second.

Fix: coalesce — set a needsLayerRebuild flag and flush on the next runloop pass, or rebuild only on mouseUp. An NSTableView would be the proper answer and would fix the scrolling item above at the same time.

Smaller itemslow

various
  • Button-group art overflows its frame. Row/column layouts place the first and last cap centres exactly on the frame edge, so half of each end cap sits outside — despite the comment at Renderer.swift:212 claiming the radius hugs the frame. The cross layout also ignores segments and always draws 4.
  • PNG and SVG text will not line up. The rasteriser centres on measured NSFont metrics; the SVG writer uses a hardcoded baselineY = midY + fontSize·0.35. Moot once text becomes paths.

  • Dead code: empty double-click branch (CanvasView.swift:512–514), _ = ps (Renderer.swift:204), _ = rowViews and the unused built array (InspectorView.swift:208–228).
  • Zoom does not preserve an anchor point — ⌘= jumps the viewport rather than zooming about the centre or the cursor.
  • README drift: "Copy/paste of elements deferred" in PLAN.md is stale (shipped in af1ddd2), and PLAN's "Rotation edited via inspector (no on-canvas rotate handle yet)" is stale too (9f695e5).
  • Uncommitted work: CanvasView.swift has the group-selection semantics change (click/marquee expands to whole group at mouse-down) sitting in the working tree. It looks correct and deliberate — commit it before touching anything else.

3 · Metrics — the numbers are right, the assumptions should be documented

ConstantValueVerdict
pixelsPerHP15 pxExactly Rack's RACK_GRID_WIDTH. 5.08 mm at Rack's 75 dpi SVG convention. Correct.
height3U380 pxExactly Rack's RACK_GRID_HEIGHT. (128.5 mm is 379.4 px; Rack itself uses the round 380, so match Rack, not the spec sheet.) Correct.
height1U127 px= 43.0 mm — this is PulpLogic-style 1U (1.7″ / 43.18 mm). Intellijel 1U is 39.65 mm ≈ 117 px and will not fit. Worth making the 1U height a preference rather than a constant, and saying which standard the current one is in the README.
SVG output spacepx, viewBox="0 0 W 380"Loads correctly in Rack. But most community tooling and the Rack docs author panels in mm space (viewBox="0 0 60.96 128.5", width="60.96mm"). An mm-space export option would improve interop with Inkscape workflows and anything downstream that assumes mm.

The inspector works exclusively in px. For panel work, a mm readout beside every X/Y/W/H field (mm = px · 25.4 / 75) would save constant mental arithmetic — and would make the 10 mm jack / 12 mm knob minimum-spacing rules checkable by eye.

4 · The missing half: from panel to plugin

Right now the tool ends at "pretty SVG". The document already contains every component centre, kind and size — the expensive information. Two exports would turn it from an illustrator into part of the build chain, and both are small:

a. A Rack helper.py components layer

helper.py createmodule reads a layer named components and infers widget positions from shape fill colour: #ff0000 params, #00ff00 inputs, #0000ff outputs, #ff00ff lights, #ffff00 custom. Emitting that layer (and stripping it from the visible artwork) means Rack generates the ModuleWidget constructor for you. Needs one new field on PanelElement — the port/param role — and roughly 20 lines in SVGExporter.

b. Direct C++ emission

addParam(createParamCentered<RoundLargeBlackKnob>(
    mm2px(Vec(15.24f, 30.48f)), module, MyModule::CUTOFF_PARAM));
addInput(createInputCentered<PJ301MPort>(
    mm2px(Vec(10.16f, 101.60f)), module, MyModule::IN_INPUT));

Element centre in px → mm is one multiply. Add an editable enumName and a widget-class string per element and the whole constructor body falls out of the document. Generating the SVG and the C++ from one source is the single most effective defence against the coordinate drift that eats time on every panel.

nice-to-have a spacing validator: flag jack centres closer than 10 mm and knob centres closer than 12 mm, and flag anything whose bounds fall outside the panel after an HP change.
