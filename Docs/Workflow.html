The .panelgen document is the only source. Artwork and headers are build output — regenerate them, never edit them.

Everything below is one loop around that rule: draw, name, emit, and then compare, which is what proves the output still matches the document it claims to come from.

1

Start the document

File ▸ New Panel

Set the width in HP and the format (3U or 1U) in the Panel section of the inspector, then fill in the two slugs. They are not the same thing and getting them the wrong way round is the most common first mistake.

FieldComes fromNames
Plugin slugplugin.json the shared widget library and its namespace — one per repository
Module slugcreateModel<…>("Muse") this panel's res/<slug>.svg, its <Slug>_panel.hpp and its namespace — one per panel

Slugs use underscores. A module slug names a file verbatim and the C++ identifiers derived from it, where a hyphen is not legal and becomes an underscore anyway; choose the hyphen and one panel ends up spelled two ways in one directory. The field corrects spaces to _ as you type, and the inspector previews what each slug will name.

Save the document into a panels/ folder inside the plugin's own repository, named after its module slug — panels/Muse.panelgen pairs with Muse_panel.hpp. The panels-check target relies on that pairing.

2

Draw the panel

Drag from the palette · double-click to drop in the centre

The left palette is banked by what things become, not by how they look:

  • Primitives — jacks, knobs, faders, LEDs, buttons, button groups, screws. These are the things that can carry a component role and reach the generated code.
  • Knobs · Position Ring — the same three knobs with the ring switched on. Deliberately separate entries: the plain ones stay what Rack draws, so a panel built from them still matches its stock widgets.
  • Shapes · Backdrop — boxes with per-corner radii, ellipses, triangles, LCARS elbows and ring sectors. Elbows plus ring sectors plus per-corner radii is how you get the Next Generation look; nothing else in the palette does it for you.
  • Symbols — waveforms, arrows, glyphs. {ka} inside a label's text places one inline at cap height.
  • Text — labels, which are artwork, not identifiers. See stage 3.
  • Stamps — your own saved fragments. Below.

Stamps: the parts of your house style

A brand mark, a wordmark, a jack pair with its labels already set — the fragments every panel of yours repeats. Select them, then Edit ▸ Add Selection to Palette… and give the stamp a name. It appears under Stamps and drops like any other palette item: drag onto the panel, or double-click to drop it in the centre.

A stamp carries shapes, sizes and colours — never identity. Component identifiers, group and label bindings are all stripped on save, so dropping the same stamp on two panels can never make them claim the same enum name. Each drop gets fresh element ids and one shared group, so it moves as a piece.

Stamps live in your library, not in the document: ~/Library/Application Support/PanelGenerator/Stamps. They are plain JSON — Edit ▸ Reveal Palette Stamps in Finder to rename, delete or hand one to someone else, then Reload Palette Stamps to pick up the change. The kurkesmurfer corner mark (5.41 × 10.94 mm, the approved painted size) and the wordmark are installed on first launch.

The wordmark is drawn, not typeset by Rack. The runtime wordmark uses the plugin's own semibold face with 0.75 px of tracking; the stamp is a text element in the system semibold and PanelGenerator has no letter-spacing parameter. Same words, same size, slightly different width. If the panel is the one being generated, that is fine — the stamp is the wordmark. If it has to sit beside a runtime-drawn one, nudge it.

Placing things

  • Snap-to-grid aligns to the HP grid — ⇧⌘G toggles it, and View ▸ Snap Step sets the division.
  • Arrow keys nudge; ⇧ + arrow moves a whole grid step. ⌘D duplicates.
  • The blue ↻ badge above a selection rotates it (⇧ snaps 15°); the orange ⇄ ⇅ badges mirror it, which is how elbows get their four orientations.
  • Edit ▸ Insert Corner Screws places all four. Screws are decoration — they never reach an enum, so their "screw" identifier is a placeholder, not a clash.
Something you can select but cannot grab is a template element — imported as a tracing underlay, drawn at half strength and deliberately immovable. Select it in the layer list and use Make Editable in the inspector to promote it to real artwork. Emit warns about any template left in a document.
3

Name what is on it

Three different things have been called "name"

WhereFieldWhat it is
Component sectionIdentifier QUANT → QUANT_PARAM in the generated enum
Text elementContent the words drawn on the panel
Layer listlayer name organisational; feeds the identifier only when Identifier is empty

A fully labelled panel can still have every component unnamed. First give each control its role — Param, Input, Output, Light, Custom, or Decoration for anything that is purely artwork — then get identifiers onto them by whichever of these fits:

  • Label Selection… ⌘L — creates text labels from the component names, one font size for the whole set. The new labels stay selected, so the inspector's Size field re-sizes all of them at once.
  • Name from Labels ⇧⌘L — the reverse: turns the labels you already drew into identifiers, pairing each control with the nearest label within 8 mm.
  • Adopt Identifiers… — copies identifiers from another .panelgen or straight from a module's .cpp, matching on the label beside each control plus its role. This is what a redesign needs: the same controls in a new layout, where position cannot pair them but the label under a knob says what the knob is in both. Matching is exact, then punctuation-insensitive (LFO 1 = LFO1), then by shared leading run (ANIM = ANIMATE, three characters minimum). Every loose match is reported.
Identifiers are numbered per enum, not per panel. Rack keeps ParamId, InputId, OutputId and LightId apart, so ANIMATE_PARAM and ANIMATE_INPUT are not a clash — a knob sharing a name with the CV input that feeds it is how modules get named.
4

Bring in what already exists

Both directions of the loop are implemented

File ▸ Import SVG… ⌘I reads a panel someone else drew, in one of two modes: as a faint tracing template you draw over, or as editable artwork you own. If the file carries a helper.py components layer, the components come with it.

File ▸ Import Module Code… ⌥⌘I reads a ModuleWidget constructor and rebuilds its components — positions, identifiers, widget types, switch frame counts — and pulls in the panel SVG it references as artwork. It resolves plugin.json beside the source for the plugin slug, evaluates the constants and helper calls it finds, and reports by line number anything it had to skip.

Centered is not decoration. createParamCentered<T>(pos, …) takes a centre; createParam<T>(pos, …) takes a top-left corner. The offset between them is the widget's own size, which lives in Rack's SVG for that type and is not knowable from the source. Uncentred calls import at the corner given and are listed by line number rather than silently offset by a guess.

Millimetres are the other trap. Rack panels are authored with the viewBox in millimetres (viewBox="0 0 71.12 128.5", width="71.12mm") while PanelGenerator works in 75-dpi pixels. The importer takes the scale from the width attribute's unit; a file without one is assumed to be pixels, and says so in the report.

5

Emit

One command, six kinds of file

PanelGenerator --emit <doc|folder> <outdir>

# or, from the plugin:
make panels-apply          # destructive: emit into the plugin
make panels-check          # emit to a scratch dir and compare

Pass a folder and every panel in it is emitted, with the plugin's widget library written once across all of them. Headers go to src/ when the output directory has one, beside res/ when it does not.

regenerated
res/<ModuleSlug>.svg
panel artwork
regenerated
res/<ModuleSlug>-components.svg
the helper.py positions layer
regenerated
res/components/<widget>-*.svg
custom widget artwork — -bg/-fg for knobs, -0…-n for switch frames, bare for ports
regenerated
<Plugin>Widgets.hpp
widget classes and aliases to Rack's stock components
regenerated
<Module>_panel.hpp
the four enums, the positions, and addComponents()
written once
<Plugin>WidgetBase.hpp
yours. Every generated widget derives from a base declared here — KnobBase, PortBase, SwitchBase, SliderBase, PlainBase — so anything a family shares (theme, shadow, tooltips, hover) has a home regeneration cannot reach. Delete it to get a fresh one.

The widget library is per plugin, not per module. Two modules using the same jack must compile to one struct loading one SVG, so emit builds the library from every panel of that plugin it can find: the ones in this run, plus any sibling .panelgen declaring the same plugin slug. Filenames come from the widget class, never from the instance — museui::KnobLarge owns knob-large-bg.svg whether it is placed once or thirty times.

6

Wire up the module

Delete the enum. Really.

addComponents() places against the enum declared in <Module>_panel.hpp, whose order is the panel's reading order — not the order the controls were written in. A module that keeps its own enum ParamId will compile cleanly and bind every control to the wrong parameter, because the two enums declare the same names with different values.

#include "Muse_ND_panel.hpp"
using namespace Muse_NDPanel;   // ids unqualified, as Rack code expects

struct MuseNDWidget : ModuleWidget {
    MuseNDWidget(MuseND* module) {
        setModule(module);
        Muse_NDPanel::addComponents(this, module);
    }
};

The module's .cpp owns the sound and nothing else.

Switches take three things, not one

app::SvgSwitch holds one frame per position and picks between them by parameter value; a button is the two-position case. Two things fail quietly:

  • momentary belongs only to a button. A momentary widget snaps back on mouse-up, so a three-position rotary declared momentary can never rest anywhere but 0.
  • The parameter range lives in the module. Three frames with the param still at 0…1 reaches two of them. Nothing in the widget can fix this, so the generated struct carries the configSwitch(QUANT_PARAM, 0.f, 2.f, 0.f, …) call for you to place.

The number of positions you drew and the Rack type you bound to must also agree — a three-position button group bound to VCVButton draws a two-position momentary button.

7

Prove it still matches

The step that catches what review does not

PanelGenerator --compare <a> <b> [--tolerance <mm>] [--no-labels]

# either side may be a .panelgen, a module's .cpp,
# or an SVG with a components layer
make compare A=~/Development/Muse/vcv/Muse.cpp B=panels/Muse.panelgen
make panels-check          # the one for CI

Every generated file carries a provenance line:

// PanelGenerator-Source: Muse ND · 25 components · digest 4717c5f5

The digest is FNV-1a over identifier, role, widget type and position in millimetres — the contract, not the artwork. Recolour the panel and it does not change; move one jack 1.25 mm and it does. --compare reads it first and says loudly when two files came from different panels, because a stale file otherwise reads as a panel full of moved and missing components. Use --no-labels against generated code, which carries no labels because PanelGenerator draws them into the artwork.

For a change to the tool itself, the round trip is the stronger test:

make selftest
make emit DOC=<doc> OUT=build/check
make compare A=<doc> B=build/check/<Module>_panel.hpp NOLABELS=1

That is what caught per-panel identifier numbering renaming five legal identifiers — code that would have compiled cleanly and bound controls to the wrong parameters. No unit test would have found it.

§

What bites, in one place

  • Millimetres, not pixels. Read a millimetre position as pixels and every component lands at a third of its proper place.
  • Centered is not decoration. Centre versus top-left corner, and the offset is unknowable from the source.
  • The generated enum owns the ids. Reading order, not writing order.
  • Identifiers are numbered per enum. Four separate enums, four separate counts.
  • One SVG per switch position, and the range lives in the module.
  • Filenames come from the class, never the instance. The namespace never appears in a filename and does not need to: res/components/ is already plugin-scoped.
  • One document per module. Two documents claiming one module slug overwrite each other's artwork and header; emit fails rather than let that pass.

The long form of each, with the reasoning, is in PIPELINE.md beside this file.

§

What the tool cannot do

Better read than discovered

  • No light/dark theme pair. One background colour per document, so createThemedPanel(light, dark) cannot be regenerated — running panels-apply on a themed plugin loses the light panel.
  • No gradients. Fills are solid; an imported gradient flattens to grey.
  • No clip paths, masks, <use> or embedded rasters on import. Each is skipped with a warning.
  • No CSS. Presentation attributes and style="…" are read; a shape styled only by a class imports unfilled.
  • <text> imports as outlines, because every Rack panel has its labels converted already — nanosvg drops text.
  • Knob rotation is not exported. Rack sweeps a knob from minAngle to maxAngle itself, so artwork is exported pointing up.
